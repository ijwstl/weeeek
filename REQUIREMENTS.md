# Weeeek MVP Requirements

## 1. Product Positioning

Weeeek is a daily/weekly reporting platform for engineering teams. It supports configurable department and project reporting, personal Git/Jira data sources, AI-assisted draft generation, reminders, visibility control, RBAC permissions, and audit logs.

The first version focuses on completing the reporting loop:

- Configure workspace, departments, project teams, templates, and reporting rules.
- Remind members to fill reports.
- Let members write or generate AI-assisted drafts.
- Let authorized leads view submitted reports, status, and summaries.

## 2. Deployment And Workspace

- The top-level isolation unit is `Workspace`.
- SaaS deployment supports multiple workspaces.
- Private deployment defaults to one workspace and can hide workspace switching.
- All business data belongs to a workspace.
- Product UI should avoid the concept of "company"; use workspace/organization settings instead.

## 3. Authentication

MVP supports:

- Feishu OAuth login.
- LDAP/AD login for private deployment.

Authentication providers:

- `feishu_oauth`
- `ldap`
- `local_password` as a later option.

LDAP MVP scope:

- LDAP login.
- Login-time user profile sync.
- Auto-create workspace member.
- Field mapping.
- TLS configuration.
- Connection testing.

Out of MVP:

- LDAP department tree sync.
- LDAP group-to-role mapping.
- SAML/OIDC SSO.

## 4. Organization Model

### 4.1 Departments

- Users can create departments.
- Departments support nesting.
- Default max depth is 5.
- Department max depth can be configured by workspace administrator.
- A user can belong to only one department.
- There is no primary department concept.
- Department report configuration can inherit from parent departments.
- Child departments may override daily and weekly templates separately.

Department report visibility:

- `private`: members can only see their own submitted reports.
- `same_department`: members of the same direct department can view each other's submitted reports.

Visibility does not include:

- Drafts.
- AI draft generation context.
- Evidence pool.
- Git/Jira raw data.
- Personal credentials.

### 4.2 Project Teams

Project teams support temporary cross-department work.

Rules:

- Project teams are flat and do not support nesting.
- Members must come from the workspace member pool.
- A user can join multiple project teams.
- Project team membership does not change department membership.
- MVP roles: project admin and project member.

Project statuses:

- `not_started`
- `in_progress`
- `at_risk`
- `delayed`
- `paused`
- `completed`
- `archived`

Project teams support:

- Project goal.
- Start date.
- Expected end date.
- Actual end date.
- Milestones.
- Risks.
- Blockers.
- Reporting rules.
- Project progress templates.
- Member progress visibility.

Project progress visibility:

- `private`: members can only view their own progress.
- `project_members`: project members can view each other's submitted progress.

Project progress can be used as personal evidence for department daily/weekly AI drafts.

## 5. ReportSpace

Use `ReportSpace` as the shared reporting abstraction.

Supported owner types in MVP:

- Department.
- Project team.

Each department and project team has one report space. `ReportSpace` owns shared reporting capabilities:

- Reporting enabled state.
- AI enabled state.
- Allowed data source types.
- Visibility policy.
- Report rules.
- Template bindings.
- Report instances.

`ReportSpace` should use `department_id` / `project_team_id` nullable columns with a database check that exactly one owner is present.

## 6. Reporting Rules

Supported report types:

- Daily.
- Weekly.
- Custom cycle for project teams.

Daily:

- Generated by natural day.
- Can skip weekends.

Weekly:

- Default week range is Monday to Sunday.
- Week start day is configurable.
- Reminder day and report period are independent.

Project custom cycle:

- Every N days.
- Every N weeks.

Reminder channels:

- In-app notification.
- Feishu notification.
- Webhook custom notification.

Report statuses:

- `pending`
- `draft`
- `submitted`
- `overdue`
- `archived`

Rules:

- Reports are generated as `pending`.
- Editing creates or updates a draft.
- Submission changes status to `submitted`.
- Late submission sets `submitted_late = true`.
- Submitted reports can be modified before deadline.
- After deadline, modifications create a new submission version.

## 7. Template System

Templates are configured by department or project team. Individual members cannot customize the department template.

Template structure:

- Template.
- Template version.
- Groups.
- Fields.

Groups are first-class template objects.

Field types:

- `text`
- `textarea`
- `rich_text`
- `table`
- `single_select`
- `multi_select`
- `number`
- `date`
- `progress`
- `member_select`
- `project_select`
- `risk_level`
- `jira_issue`
- `git_ref`
- `url`

Table field:

- Used for structured multi-row content such as completed work, plans, risks, and blockers.
- Supports configurable columns.
- Does not support nested table fields.
- Stores column snapshots in submitted reports.

Template version rules:

- Published versions are immutable.
- Editing creates or updates a draft version.
- Publishing creates a new version.
- Each template can have only one draft.
- New reports use the active published version.
- Existing drafts keep the version used when they were created.
- Submitted reports always render from submitted content snapshots.

Submitted reports must store:

- Template ID.
- Template version ID.
- Group snapshots.
- Field snapshots.
- Table column snapshots.
- Field values.

## 8. AI Draft Generation

AI configuration is personal, not department-owned.

Report spaces may allow or disallow AI and data source types. Users decide whether to authorize and use their own data sources.

AI generation requires the intersection of:

- Report space allows AI.
- Field supports AI assistance.
- User has AI enabled.
- User has authorized the selected data sources.
- User has permission to access the selected data.
- User selects the sources for the current generation.

MVP data sources:

- GitHub.
- GitLab.
- Jira.

Git MVP fetches:

- Commits.
- PR/MR title, description, status, link, branch, time.

Git MVP does not fetch:

- Code diff.
- File-level changes.
- Review comments.

Jira MVP fetches:

- User-related issues.
- Issues created in the report period.
- Issues with status changes in the report period.
- Current status.
- Priority.
- Assignee.
- Reporter.
- Comment summary.
- Project.
- Link.

Jira MVP does not fetch:

- Full comment history.
- Attachments.
- Detailed work logs.
- Deep Sprint/Epic structures.

AI generation behavior:

- User manually clicks generate.
- User selects sources and fields.
- Default mode fills empty fields only.
- Overwrite requires explicit user confirmation.
- Generated output is a draft only.
- User must submit manually.
- Failure of one source should not block generation from other available sources.

Evidence cache:

- Raw fetched data is short-lived.
- Default cache retention is 7 days.
- Submitted reports permanently store report content and source references, not full raw Git/Jira data.

## 9. Data Sources

Workspace integration providers:

- GitHub.
- GitLab.
- Jira.

User data sources:

- Belong to individual members.
- Store encrypted credentials.
- Store account mappings.
- Store scope configuration.
- Can be tested, disabled, refreshed, or deleted by the owner.

Admins cannot view user credential plaintext.

## 10. Notification System

Use plugin-style notification channels.

Concepts:

- Notification rule.
- Notification event.
- Notification.
- Notification delivery.
- Notification channel plugin.

MVP channels:

- `in_app`
- `feishu`
- `webhook`

Webhook MVP supports:

- URL.
- POST method.
- Headers.
- Secret.
- Payload template.
- Timeout.
- Retry count.

Notification failures do not block reporting flows. Failures must be recorded and retryable.

## 11. RBAC Permissions

Use permission-based RBAC.

Model:

- Member has role assignments.
- Role has permissions.
- Permission is identified by a stable code.
- Role assignment has a scope.

Scope types:

- `workspace`
- `department`
- `project_team`
- `self`

Permission code format:

- `resource.action`

Examples:

- `department.read`
- `department.create`
- `department.update`
- `department.delete`
- `department.member.manage`
- `department.rule.manage`
- `department.template.manage`
- `department.report.view`
- `department.report.summary`
- `project.read`
- `project.create`
- `project.update`
- `project.archive`
- `project.member.manage`
- `project.rule.manage`
- `project.template.manage`
- `project.progress.view`
- `project.summary.view`
- `report.read.own`
- `report.submit.own`
- `report.update.own`
- `report.read.space`
- `report.export`
- `template.create`
- `template.update`
- `template.publish`
- `datasource.manage.own`
- `datasource.provider.manage`
- `workspace.member.manage`
- `workspace.role.manage`
- `workspace.setting.manage`
- `workspace.audit.view`
- `ai.generate.own`
- `ai.summary.space`
- `notification.channel.manage`
- `notification.rule.manage`

Built-in roles:

- Workspace owner.
- Workspace admin.
- Integration admin.
- Department admin.
- Department lead.
- Project admin.
- Project member.
- Member.

Workspace admins do not view all report bodies by default. Workspace owner can configure that policy.

## 12. Audit Logs

Audit logs are mandatory for sensitive operations.

Audit implementation:

- FastAPI decorator for operation-level audit.
- Middleware for request context.
- Service-level audit for background tasks.

Audit records include:

- Workspace.
- Actor member.
- Action.
- Resource type.
- Resource ID.
- Target member.
- Permission code.
- Scope type.
- Scope ID.
- IP.
- User agent.
- Request ID.
- Request method.
- Request path.
- Status.
- Metadata.
- Created time.

Never store in audit metadata:

- Tokens.
- Passwords.
- Full prompts.
- Full code diffs.
- Jira attachments.

Mandatory audit events:

- Login success/failure.
- Role grants and revokes.
- Department changes.
- Project team changes.
- Template publishing.
- Reporting rule changes.
- Report view, submit, late submit, export.
- Data source bind, disable, delete.
- AI draft generation.
- Workspace security setting changes.
